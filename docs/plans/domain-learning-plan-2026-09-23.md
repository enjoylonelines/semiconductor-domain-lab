이 문서는 Track A의 도메인 학습·자기 설명 수락 기준을 보존한다. 현재 Track A/B 제품 범위와 확장·종료 판단은 [범위 정본 §0](research-and-scope-2026-09-23.md)을 따른다. 아래 “이번 요청/미착수/후속 생성”은 최초 학습 계획 당시의 기록이다. 현재는 Track B의 src/tests 및 Stage 1~3 evidence가 존재하므로 저장소 전체의 미착수 상태로 읽지 않는다. Track B 코드·저장된 테스트 보고는 사용자의 이해 검증이나 아래 6종 Track A 수락 사례 완료를 대신하지 않는다. 이번 검토에서는 실행하지 않았다.

## 1. 목적·비범위

이 저장소는 MCU를 사용하던 임베디드 관점에서 칩 내부의 IP와 개발·검증 흐름을 이해하고, HW 엔지니어를 돕는 SW 업무를 설명하기 위한 학습 저장소다. 반도체 설계 직무로 전환하는 훈련이나 새 포트폴리오 서비스가 아니다.

완료 후 남길 것은 도메인 지도, EDA 흐름, 용어와 업무 예문, 작은 Python 파서 실험 1개, JD 연결 문서, 과장 없는 면접 설명이다. 이번 요청에서는 이들의 **계획과 조사 근거만** 작성한다.

비범위:
- 실제 PHY/SerDes/RTL 설계, 회로 구현·최적화, 고급 타이밍 분석 능력 확보.
- 상용 EDA 설치·라이선스 취득, 대형 오픈소스 EDA 환경 구축, 실제 칩 제작.
- FastAPI 등 새 서버, 웹 UI, 데이터베이스 서버, Kafka/Redis, 컨테이너·CI 서버 구축.
- FPGA·MCU 보드 구매/펌웨어 신규 구현, 실제 계측·신호 품질 인증.
- 외부 저장소 생성·공개, 커밋·푸시. 로컬 Git 초기화만 허용한다.
- 채용공고에 나오는 기술을 전부 실험에 끼워 넣는 것.

기존 SW 프로젝트의 DB·동시성·운영 증거와 역할을 분리한다. 이 저장소가 입증하는 것은 **도메인 이해 및 제한된 데이터 처리 연습**이다.

## 3. Domain Map — 신호 경로와 개발 업무를 분리

아래는 **S: 관계를 배우기 위한 지도**다. MCU→SoC는 제품이 반드시 변하는 순서가 아니라 학습 관점의 이동이며, MCU도 넓은 의미의 시스템 집적 칩일 수 있다. IP는 완성 칩과 같은 것이 아니라 재사용·통합할 설계 자산이다.

```text
익숙한 임베디드 시스템
  센서/주변장치 ↔ MCU(프로세서·메모리·주변회로) ↔ 펌웨어
                         │ 칩 내부를 들여다보는 학습
                         ▼
SoC: CPU·메모리 관련 블록·기타 기능 + 여러 반도체 IP
  └─ 인터페이스 IP: 규칙을 처리하는 controller + 신호를 주고받는 PHY
      ├─ PCIe: 시스템의 장치 간 연결, PHY에 고속 직렬 송수신 기술
      ├─ UCIe: 패키지 안의 칩렛 간 연결, 별도의 PHY·계층 구조
      └─ MIPI 계열: 카메라/디스플레이 등
          └─ 예: CSI-2/DSI-2 controller + C-PHY/D-PHY

SerDes: 병렬↔직렬 변환 및 고속 송수신을 이해하는 핵심 기술
  └─ 모든 PHY나 모든 인터페이스를 동일한 SerDes 블록으로 치환하지 않음

[위 블록들을 만들고 검증하는 개발 활동]
  설계·분석·검증에 EDA 활용 → log/report/result
  → Python 데이터 처리 → API/DB/queue/자동화로 SW 업무 연결
```

핵심 경계:
1. Controller/PHY 구분은 S이다. 실제 논리 물리 계층과 전기 회로의 분할·제공 범위는 규격/제품별로 다르다.
2. PCIe, UCIe, MIPI는 연속적인 하위 단계가 아닌 **비교할 인터페이스 계열**이다.
3. UCIe는 패키지 내 다수 데이터 레인과 전달 클록을 쓰는 구조를 알아본다. 각 레인에 시간에 따른 비트 전송이 있다는 것과 일반적인 장거리 SerDes 링크 구조가 같다는 것은 별개다. T1/T2/T4.
4. MIPI는 여러 규격의 묶음이다. 이 학습에서는 카메라/디스플레이용 CSI-2/DSI-2 및 C/D-PHY만 짧게 다룬다. T3/C1.
5. EDA는 신호가 PHY 다음에 통과하는 장치가 아니다. 위 설계를 개발·검증할 때 쓰는 도구·방법이다.
6. 실물 칩에서 검증했다는 의미와 시뮬레이션에서 검증했다는 의미를 분리한다. IP 제품과 고객 SoC의 최종 검증 책임도 같지 않다.

검증 과제: 빈 종이에 그림을 그리고 “MCU 펌웨어 경험이 PHY 회로 설계 경험을 뜻하는가?”, “왜 UCIe를 PCIe 선의 연장으로 그리면 안 되는가?”, “EDA는 그림 어디에 놓이는가?”를 각각 2문장으로 답한다.

## 4. EDA Workflow Map — 디지털·아날로그·PHY

### 4.1 디지털 로직의 큰 흐름
**F 근거 E1/K1/K2, 아래 배열은 S.** 검증은 simulation 이후 한 번 하는 단계가 아니라 설계 전반의 활동이다.

```text
요구사항/검증 계획
  → RTL 설계
  ↔ simulation 및 기능 verification
  → synthesis → gate-level netlist
  → floorplan → placement → clock tree → routing
  ↔ 타이밍·전력·물리 규칙 분석 / 설계 수정
  → sign-off 검토 → tape-out용 최종 설계 전달

검증은 전 과정에 반복:
기능 검증, 논리 동등성, 제약 확인, 정적 타이밍, 물리 검증 등
```

EDA 튜토리얼의 순서는 대표 예다. 합성 이후에도 기능·동등성 검증이 있고, timing 분석은 배선 후 한 번만 하는 것이 아니다. OpenROAD를 읽었다고 회사가 그 도구를 사용한다고 말하지 않는다.

### 4.2 아날로그/혼성 신호의 큰 흐름
**F 근거 E3/K1, 아래 배열은 S.**

```text
사양/회로 구조
  → schematic(회로도)
  ↔ 회로 simulation / 공정·전압·온도 조건별 확인
  → custom layout
  → 기생 성분 추출 → 추출 성분을 포함한 재시뮬레이션
  ↔ DRC/LVS·신뢰성·전력/신호 관련 분석
  → sign-off 검토 → 최종 설계 전달
```

이 흐름을 모두 “RTL 합성→자동 배치배선”으로 표현하지 않는다. 디지털 제어 부분과 아날로그 송수신 회로가 함께 있는 PHY에서는 두 흐름과 모델 간 연결을 이해하는 것이 핵심이다. 통계적 소자 편차 분석 등 세부 방법은 backlog로 보낸다.

### 4.3 PHY/IP와 실리콘 검증을 연결
**F: C2/T5/K6, I/S: 아래 업무 연결.**

- 제조 전: 디지털 제어 동작, 회로 조건, 채널 모델을 통한 신호 품질 등의 확인.
- IP integration: 고객 설계에서 연결·설정·타이밍·물리 조건이 맞는지 확인.
- 제조 후: 실물 칩과 평가 환경에서 동작 확인. BIST, BER, eye diagram은 이 맥락 또는 모델 기반 분석에서 등장할 수 있다.
- BER 숫자에는 관찰 비트 수·조건·실측/추정 여부가 필요하다. 오류 0회를 “오류 확률 0”이라고 말하지 않는다.
- timing violation과 BER 실패는 같은 종류의 지표가 아니다. 하나의 가짜 보고서에 무리하게 섞지 않는다.

### 4.4 산출물 읽기

| 구분 | 의미·대표 예 | SW가 보존할 맥락 | 검증 질문 |
|---|---|---|---|
| log / 로그 | 실행 순서·경고·오류·종료 정보 | 실행 ID, 도구/설정, 원문 줄 위치 | 실행 완료와 설계 통과는 같은가? |
| report / 리포트 | 타이밍·면적·검증 결과 등 정리된 분석 | 단위, 분석 조건, 검사 종류, 요약/상세 구분 | worst slack 하나로 칩 합격을 선언할 수 있나? |
| result / 결과 산출물 | 회로 연결 정보·파형·레이아웃 등 | 생성 단계, 버전, 파일 경로·체크섬 | 모든 result가 텍스트인가? |

E2에서 logs/reports/results를 관찰할 수 있으나, 이 명칭·구조가 모든 EDA 도구의 공통 규약은 아니다. 바이너리나 독점 포맷 파싱은 범위 밖이다.

## 5. SW Engineer Touchpoints 및 JD 매핑

아래의 **업무 요구는 J0/J2/J3/J4의 F**, 구체적인 상황·데이터 모델·운영 해법은 **I/S**다.

| HW/IP 개발 상황 → SW 접점 | 연결되는 JD | 이번 학습·검증 | 이번에 구현하는가? |
|---|---|---|---|
| 여러 실행 결과를 모아 로그/리포트의 필드를 정형화 | 파일 파싱·데이터 가공, Python | 누락·음수·단위·부분 실패를 다룬 파서 계약과 실험 | 후속 실행 때 파서 1개만 |
| 사용자가 실행 결과·조건을 조회 | RESTful API | 실행 ID와 결과 조회를 1개 요청/응답 그림으로 설명 | 서버 구현 안 함 |
| 오래 걸리는 작업을 요청과 분리 | 메시지 큐·비동기 이벤트 | 요청 수락과 완료의 차이, 재시도/중복을 종이 사례로 설명 | 큐 설치 안 함 |
| 여러 실행·조건·측정값을 검색·비교 | RDB 모델링·쿼리 최적화 | Run–Artifact–Metric 관계와 단위/버전 분리, 조회 패턴 2개 | DB 설치·성능 측정 안 함 |
| 진행 상황을 사용자에게 전달 | Redis Pub/Sub 실시간 데이터 | 임시 알림과 보존되는 결과의 차이, 재연결 시 조회 필요성 | 실시간 전송 안 함 |
| 저장 항목 추가 또는 파서 버전 변화 | migration·안정적 운영·리팩토링 | 기존 데이터와 새 결과의 호환 및 되돌리기 계획 5줄 | migration 실행 안 함 |
| 자동화 도구 수정의 회귀 방지 | 테스트·CI/CD·컨테이너 운영 | 정상/깨진 입력 테스트와 배포 전 확인 항목을 설명 | 파서 테스트만 후속 실행; 배포 없음 |
| HW 엔지니어의 반복 작업과 의미 확인 | in-house tool, HW 협업, 사용 가이드 | “완료/실패는 무엇인가, 단위는 무엇인가” 질문 5개 및 짧은 사용법 | 별도 도구 추가 안 함 |
| 보드의 상태·설정을 소프트웨어로 다룸 | 과거 MCU firmware/Web 맥락 | 기존 임베디드 경험에서 사실 확인 가능한 연결 1개 | 새 firmware/Web 없음 |

설명용 상태 모델(S):
`QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELLED`.
여기서 SUCCEEDED는 **작업 실행** 의미로 제한한다. 설계 검사 `PASS/FAIL/UNKNOWN`과 데이터 처리 `OK/PARTIAL/INVALID`는 독립적으로 둔다. 이는 회사의 상태 모델을 확인한 것이 아니다.

종이 사례 3개:
1. 실행이 정상 종료했지만 timing slack이 음수 → 작업 완료와 설계 제약 미충족을 동시에 표현.
2. 도중에 종료되어 값이 없음 → 0 또는 PASS로 바꾸지 않고 UNKNOWN/누락 이유 보존.
3. 같은 결과를 두 번 수신 → 실행·산출물 식별자와 내용 체크섬으로 중복을 식별하는 방안을 설명. 실제 전달 보장은 해당 제품 문서로 후속 확인.

DB 학습 예(S): Run(실행 정보)–Artifact(원문 위치·체크섬)–Metric(값·단위·검사/조건).
조회 예는 “같은 조건의 실패 실행”과 “동일 설정의 두 실행 비교” 2개로 제한한다. 인덱스·정규화·쿼리 최적화는 가설을 설명하는 수준이며 성능 개선을 입증했다고 말하지 않는다.

## 6. Terminology Glossary 작성 규칙

[용어 계획 및 초기 표](terminology-plan.md)를 사용한다. 도메인뿐 아니라 SW 연결 용어도 적용 대상이다.

모든 전문용어는 최초 등장 또는 연결된 표에 다음을 갖춘다:
**영문 원어/약어 + 국내 실무 한국어 표기·호칭 + 독음(또는 미확인) + 한 줄 의미 + 실제 업무에서 쓸 법한 문장 + 관련 단계 + 정의 출처 + 한국어 용례 출처 + 확인 상태.**

- 영어 그대로 쓰는 용어를 억지 한자어로 바꾸지 않는다.
- 작성한 업무 예문은 전부 S이며 실제 직원의 발언·사내 절차처럼 인용하지 않는다.
- 정의 근거와 발음 근거를 분리한다. 정의가 확인되어도 독음은 U일 수 있다.
- 첫 목표는 핵심 20개를 자기 말로 설명하는 것. 나머지는 보고서를 읽을 때 찾아보는 표다. 표에 있다는 이유로 모두 암기하지 않는다.
- 호칭을 “흔히 쓴다”고 확정하려면 가능한 한 서로 독립적인 한국 기업·교육기관 자료 2개를 대조한다. 자료가 부족하면 관찰된 표기 또는 읽기 가이드로 한정한다.
- “서데스”는 회사 공시 C4로 확인. “시스템온칩”은 K9, “합성/배치 및 배선/사인오프/테이프아웃”은 K3/K4, “아이 다이어그램”은 K6/K7로 확인.
- PHY는 “PHY / 물리 계층”을 우선 표기한다. “파이”는 K10에서 관찰, “피지”의 현업 통용성은 미확인이다. 예시를 근거 없이 정답으로 굳히지 않는다.
- 발음 추가 조사에는 전체 30분 상한. 확인되지 않은 사내 구두 호칭은 U로 남겨도 완료 가능하다.

## 7. 작은 hands-on 실험 계약 — 아직 구현하지 않음

**S: synthetic EDA-like timing summary → Python parser → JSON 구조화, 단 한 가지 포맷.**

선택 이유: 로그·리포트 처리 JD와 직접 연결되며, 상태·누락·단위 해석을 작게 검증할 수 있다. 특정 상용 도구의 파서를 만들었다고 주장하지 않는다.

입력 계획:
- 직접 작성한 UTF-8 텍스트 최대 6개, 파일당 50줄·전체 10KB 이내.
- 각 파일에 `SYNTHETIC / NOT GENERATED BY AN EDA TOOL` 표시.
- 공통 필드: fixture_format_version, run_id, stage, corner_label, check_type, tool_exit_code, worst_slack, unit, elapsed_seconds.
- corner_label은 TT/SS 등의 물리 의미를 검증했다는 뜻이 아닌 조건 식별용 가상 문자열이다.
- tool_exit_code도 가상 데이터이며 실제 EDA 프로세스를 실행하지 않는다.
- 공개 EDA 자료는 출력 종류와 의미를 이해하는 근거로만 읽는다. 30분 안에 정확한 라이선스·버전·샘플 출처를 확보하지 못하면 공개 데이터 복제 없이 synthetic 방식 유지.

출력 계약:
- Python 표준 라이브러리로 파일 입력→JSON 한 개, 키와 레코드 정렬 고정.
- source_kind=synthetic, fixture_format_version, parser_version, source_path, source_sha256, 원문 줄 번호를 남김.
- job_status(실행), parse_status(파싱), timing_status(해당 검사)를 분리.
- worst_slack_ns와 원래 값·단위·check_type·corner_label을 함께 보존.
- ps→ns 변환만 지원. 지원하지 않는 단위·버전은 명시적 오류, 없는 값은 null과 이유.
- 음수 slack이면 해당 가상 검사만 FAIL. 양수여도 입력이 불완전하면 전체 설계 PASS를 추론하지 않음.
- UNKNOWN은 검사 정보 부족, INVALID는 입력 계약 위반으로 구분.
- 완전한 입력은 종료코드 0, 일부 결과만 읽었으면 2, 입력 계약 전체 위반이면 1로 계획. 모두 문서화하며 실제 EDA 종료코드와 혼동하지 않음.

수락 사례(미실행):
| 사례 | 기대 결과 |
|---|---|
| 정상 종료·완전한 report, +0.12 ns | 실행 SUCCEEDED, 파싱 OK, 해당 timing 검사 PASS |
| 정상 종료·완전한 report, -0.08 ns | 실행 SUCCEEDED, 파싱 OK, 해당 timing 검사 FAIL |
| 중단되어 slack 누락 | 실행 실패 또는 미확인, 파싱 PARTIAL, timing UNKNOWN |
| -80 ps | -0.08 ns로 변환, 원래 단위 보존 |
| 숫자 손상·지원하지 않는 단위/버전 | 명시적 INVALID; 0/PASS로 대체 금지 |
| 필수 필드 중복·충돌 | 오류로 식별; 마지막 값으로 조용히 덮어쓰기 금지 |

같은 입력의 반복 실행 결과가 같고 원문 근거로 되돌아갈 수 있어야 한다. 순서 변경·빈 줄 정도는 포맷 계약에 따라 허용 여부를 정한다. 프로젝트 확장이 아닌 데이터 처리 의미를 확인하는 작은 테스트만 작성한다.

후속 실행 산출물 계획:
- `experiments/parser/`: 구현·synthetic 입력·기대 결과·작은 테스트.
- `docs/evidence/parser-result.md`: 명령, 실행 환경, 결과, 실패 사례, 한계.
- 이 디렉터리와 파일은 이번 요청에서 생성하지 않는다.
- 구현 예산 3시간. 막히면 의존성을 추가하지 않고 포맷을 줄인다. 타임박스를 넘기면 미완료 상태와 막힌 점을 기록하고 중단한다.

## 10. Stop Rule·백로그·완료 증거

다음 다섯 항목을 모두 만족하면 학습을 종료한다. 현재는 모두 미완료다.

- [ ] SoC/IP/PHY/SerDes/PCIe/EDA 관계를 자료 없이 자기 말로 설명하고 UCIe/MIPI의 위치도 구분한다.
- [ ] 디지털·아날로그 EDA 흐름의 차이와 주요 log/report/result를 각각 설명한다.
- [ ] Python/backend 개입 지점을 3개 이상 말하고 실행 완료·파싱 성공·설계 검사 통과를 구분한다.
- [ ] 작은 파서 실험 1개와 6종 수락 사례·재현 방법·synthetic 표시가 남아 있다.
- [ ] JD의 SW 업무가 반도체 조직에서 필요한 이유를 설명하되 실제 요구와 추론을 구분한다.

**성공 종료와 시간 만료를 구분한다.** 12시간이 끝났는데 필수 항목이 부족하면 “학습 미완료”로 기록하고 실행을 멈춘다. 자동으로 4일차·2번째 실험·새 서비스를 추가하지 않는다. 후속 범위 변경은 별도 요청으로 다룬다.

추가 주제는 `주제 / 발견 계기 / 지금 필요하지 않은 이유 / 다시 볼 조건` 네 칸으로 backlog에만 기록한다.
초기 backlog: 고급 SerDes 회로·DFE/CTLE 수식, PCIe/UCIe 상세 상태 전이, 실제 EDA job scheduler, 상용 파일 형식, 대규모 DB 성능, MCU 장비 연동, CI/CD 배포. 두 번째 parser·웹 UI는 이번 종료 조건에 들어가지 않는다.
